## Remote/Reverse Port Forwarding with SSH

### The Problem: "I can't hear you!"

Imagine you are the **Attacker** and you want to talk to the **Windows Target**.

- **The Issue:** The Windows Target is locked in a room (a private network). It cannot send messages directly to you. It doesn't know where you are or how to reach your IP address.
    
- **The Opportunity:** There is a guy standing in the hallway, the **Ubuntu Server** (the Pivot).
    
    - The Windows Target **can** talk to the Ubuntu Server.
        
    - You **can** talk to the Ubuntu Server.
        

### The Solution: The "Middleman" Trick

Since the Windows Target cannot connect to you, we have to trick it. We will tell the Windows machine: _"Hey, don't try to call me. Call the Ubuntu Server instead."_

Then, we tell the Ubuntu Server: _"If anyone calls you on phone number **8080**, instantly forward that call to me on my phone number **8000**."_

### Visualizing the Traffic Flow

Here is how the data actually moves. This is the most important part to understand:

1. **The Malware (Payload):** You put a virus on the Windows machine. You configure it to connect to the **Ubuntu Server's IP** on port **8080**.
    
2. **The Forward (SSH -R):** The connection hits the Ubuntu Server. Because you ran the `ssh -R` command, Ubuntu picks up that traffic and pushes it through your existing SSH connection.
    
3. **The Catch (Listener):** The traffic pops out on **your Local Machine** on port **8000**, where your Metasploit is waiting to catch it.

Similar to the pivot proxy above, there could be scenarios when we cannot directly pivot to an external server (attack host) on the cloud. Some organizations have [HTTP-proxy with NTLM authentication](https://docs.microsoft.com/en-us/openspecs/office_protocols/ms-grvhenc/b9e676e7-e787-4020-9840-7cfe7c76044a) configured with the Domain Controller. ```shell-session


After configuring the `portproxy` on our Windows-based pivot host, we will try to connect to the 8080 port of this host from our attack host using xfreerdp. Once a request is sent from our attack host, the Windows host will route our traffic according to the proxy settings configured by netsh.exe.
